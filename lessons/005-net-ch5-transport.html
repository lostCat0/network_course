运输层：从「送到主机」到「交给程序」

网络层已经能把 IP 数据报送到全世界任何一台主机了。但请想一个新问题：你电脑上同时开着浏览器、微信、音乐播放器，百度回来的包凭什么交给浏览器而不是微信？IP 地址只精确到主机，还差最后一公里——进程。

运输层的使命：为主机间的进程通信提供逻辑信道。两个协议代表两种截然不同的服务哲学——UDP 是「平信」：不连接、不保证、不重传，但快且轻；TCP 是「挂号回执专递」：先握手建立连接、逐字节确认、丢了重传，慢一点但可靠。学完本章你要能回答：什么场景选 UDP（直播、DNS、游戏），什么场景必须 TCP（网页、文件传输、支付）。

一、端口与套接字：进程的「门牌号」

端口号 16 位（0~65535），标识主机内的通信端点。分类：

  • 熟知端口 0~1023：HTTP 80、HTTPS 443、DNS 53、FTP 21、SSH 22、SMTP 25——服务器服务的固定门牌。
  • 登记端口 1024~49151：给没有熟知端口的应用登记使用。
  • 短暂端口 49152~65535：客户端临时取用，用完归还。看第3章真实抓包：你的浏览器连 443 端口时，本地用的 60844、53761 就是短暂端口。

套接字（Socket）= (IP 地址 : 端口号)。TCP 连接由一对套接字唯一标识——所以一台服务器 443 端口能同时维持成千上万条连接，靠的是对方 IP:端口不同来区分。这是简答常考点。

二、UDP：把「简洁」做到极致

UDP 首部仅 8 字节：源端口 2B + 目的端口 2B + 长度 2B + 校验和 2B。特点四连（简答背诵）：

  • 无连接：发送前不握手，拿起来就发；
  • 尽最大努力交付：不保证可靠，不确认不重传；
  • 面向报文：应用交来多长就发多长，不合并不拆分（一次交一份）；
  • 没有拥塞控制：网络拥堵也不减速——这正是实时音视频（宁丢帧不等待）和 DNS 偏爱它的原因。

校验和可选（全 0 表示不校验），伪首部只参与计算不传输——细节知道即可。

三、TCP：可靠传输的全部秘密

3.1 面向字节流

TCP 把应用交来的数据视为无边界的字节流，切分成大小合适的报文段（segment）发送。「面向字节流」的后果：接收方 TCP 交给应用的数据可能和发送方写入的「一次一块」完全不同——分块是 TCP 自己决定的。这也是「粘包」问题的根源（应用层要自己定边界），深入理解这点是面试高频。

3.2 首部关键字段

固定首部 20 字节。必考字段：序号 seq（本报文段数据第一个字节的编号）、确认号 ack（期望收到的下一个字节序号 = 已正确收到的最后字节 +1，含义是「累积确认：这之前的都收到了」）、窗口（接收方剩余缓存，用于流量控制）。6 个控制位里记四个：SYN（建连）、FIN（释放）、ACK（确认号有效）、RST（复位，异常终止）。

3.3 三次握手（先看真实抓包再记图）

在我为你抓的样本流量里就有大量 TCP 连接（443 端口的 HTTPS）。握手三步，A=客户端 B=服务器：

① A → B : SYN=1, seq=x            （A：我想建立连接）
② B → A : SYN=1, ACK=1, seq=y, ack=x+1   （B：同意，同时我也开一条）
③ A → B : ACK=1, seq=x+1, ack=y+1 （A：收到，双方各自完成）

为什么恰好三次，不是两次？关键在第二次报文的双重身份（SYN+ACK 合并）。若只有两次：A 发 SYN，B 回 ACK，连接就算建立了——但这个 SYN 若是网络中滞留的失效请求（A 早已放弃），B 单方面建立连接、傻等数据，资源白白占用（半连接漏洞）。第三次握手让 A 有机会「确认双方都确认过了」，失效请求自然作废。为什么不是四次？因为 B 的 SYN 和 ACK 合并成一报发送，没有必要拆开（这是 2020 年后的新考法，注意）。

3.4 四次挥手与 TIME_WAIT

① A → B : FIN=1, seq=u     （A：我发完了）
② B → A : ACK=1, ack=u+1   （B：知道了——但我可能还有话说）
   （此时连接处于半关闭：A→B 方向关闭，B 仍可发数据）
③ B → A : FIN=1, seq=w     （B：我也发完了）
④ A → B : ACK=1, ack=w+1   （A：收到，再见）
A 在收到第④步确认前要等待 2MSL 才真正关闭

两个经典问答：①为什么挥手要四次而握手三次？因为 TCP 全双工，两个方向独立关闭；B 收到 FIN 时可能还有数据没发完，ACK 和 FIN 不能合并（握手时 SYN+ACK 能合并）。②为什么 A 要等 2MSL（最长报文段寿命的 2 倍）？保证最后一个 ACK 能重传一次（若 B 没收到会重发 FIN），且让本连接中所有旧报文在网络中消亡，避免污染下一个相同端口的连接。

3.5 可靠传输：滑动窗口一以贯之

从简单到精巧的演进链（理解这个链路比背名词重要）：

  • 停止等待：发一包等一确认——太慢，信道利用率低；
  • 连续 ARQ + 滑动窗口：一口气发窗口内所有字节，收到确认窗口向前滑——效率高；
  • 超时重传：计时器到点未确认就重传。超时时间 RTO 依据 加权平均往返时间 RTTs 动态调整（RTTs = (1−α)×旧RTTs + α×新样本，α 常取 1/8——计算题会考）；
  • 累积确认的漏洞 → SACK：只确认连续部分，中间丢的段要等超时。看第3章真实抓包第 3 帧的标志：SLE=1 SRE=2——这就是 SACK（选择确认）在真实网络里的样子，告诉对方「1~2 号块我也收到了」。

3.6 流量控制 vs 拥塞控制（易混，务必分清）

流量控制拥塞控制
怕什么接收方缓存装不下网络（路由器）撑爆
谁控制点对点（收方用窗口字段钳制发方）全局性（发方自己探测网络）
机制滑动窗口（rwnd）慢开始、拥塞避免、快重传、快恢复（cwnd）
实际发送窗口min(接收窗口 rwnd, 拥塞窗口 cwnd) —— 两个都要听

拥塞控制四算法必须会画 cwnd 演变图（经典考题）：慢开始阶段每 RTT 翻倍（1→2→4→8），达到慢开始门限 ssthresh 后转拥塞避免线性 +1（8→9→10…）；一旦超时，ssthresh = 当前 cwnd/2，cwnd 重置 1 重新慢开始；若收到 3 个重复 ACK 则触发快重传（立即重发丢失段）+ 快恢复（ssthresh=cwnd/2，cwnd=ssthresh 直接进入拥塞避免，不回到 1）。

例题：ssthresh=8, cwnd 从 1 开始慢开始。写出 cwnd 变化：
1 → 2 → 4 → 8（到达门限）→ 9 → 10 → 11 …（拥塞避免，每 RTT +1）
若 cwnd=10 时超时：ssthresh = 5, cwnd = 1，重新慢开始：
1 → 2 → 4 → 5（到达新门限）→ 6 → 7 …

四、🧪 动手实践（本章 2 个实验）

实验 1：Wireshark 亲手抓三次握手 + 挥手

1. Wireshark 开始抓包，过滤器：tcp.flags.syn==1 || tcp.flags.fin==1
   （只看建连和挥手瞬间）
2. 浏览器新标签页打开一个网站（如 http://example.com 用 http 抓得到明文握手）
3. 找一对 SYN / SYN,ACK / ACK——三次握手三行，右键 Follow → TCP Stream
   观察任务：
   a. 相对序号（Wireshark 显示 Relative seq）：SYN 的 seq=0，
      服务器回的 ack=1 —— 验证 ack = 对方 seq+1
   b. SYN 和 FIN 都占 1 个序号但都不携带数据（教科书原话在抓包里的样子）
   c. 挥手侧：FIN 四步走，观察两方向的 seq 是否独立推进
4. 高级：过滤器 tcp.analysis.retransmission
   ——看有没有真实网络的重传报文（你 RTT 波动大时几乎必然出现）

实验 2：Packet Tracer 仿真模式看 TCP 全程

1. 拓扑：PC0 连 Server0（Server 的 HTTP 服务默认开启）
2. PC 配 IP 与网关，先在 PC 的浏览器里访问一次服务器 IP 确认能通
3. 切到 Simulation 模式，Edit Filters 只勾选 TCP
4. PC0 浏览器再访问服务器，点 Play 一帧一帧看：
   SYN → SYN,ACK → ACK → HTTP GET → HTTP 响应 → FIN/ACK 四步
5. 点击任意报文可看 OSI Model 分层视图——
   对照第3/4章学过的以太网帧、IP 首部在这里一层层套着
6. 思考题：把 Server 的 HTTP 服务关掉再访问，抓到的应答是什么？
   （RST——连接被拒绝，RST 控制位的真实用途）
